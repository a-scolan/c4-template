`async` is valid in this workspace because it is defined in `projects/shared/spec-global.c4`, so LikeC4 no longer complaining only proves syntax and shared-vocabulary validity, not semantic correctness.
To validate the model, ask three questions: 1) Is the interaction really fire-and-forget or message-driven? 2) Is there buffering, retry, or later processing? 3) Would the sender continue without waiting for an immediate response? If the answer is no, `calls` was probably the correct relationship.
The repo's own example in `projects/spec-showcase/containers.c4` uses `async` for messaging flows such as `api -> queue` and `queue -> processing_server`, not as a generic replacement for request/response. That is why a direct `async` between two normal application containers can render oddly even though it parses.
So validate semantically, not just syntactically: keep `calls` for synchronous HTTP-style interactions; use `async` for dispatch to a queue, event bus, or background worker; and if the flow is truly asynchronous, consider modeling the missing mediator explicitly with `Container_Queue` and, for the worker, `Container_ProcessingServer`.
