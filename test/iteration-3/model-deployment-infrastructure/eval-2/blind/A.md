If production runs on managed Kubernetes and you do not know the underlying hosts, do not invent hidden physical VMs just to force the diagram into a VM-shaped model. Keep an explicit deployment hierarchy at the level you actually know. In this repository, `Node_Cluster` exists in the shared deployment spec, so an honest structure is `Prod = Node_Environment -> AppTier = Zone -> ProdK8s = Node_Cluster -> apiApp/uploadApp/workerApp = Node_App`. Then wire each runtime node back to the logical model with `instanceOf`, for example `apiApp instanceOf documentPlatform.apiGateway`, `uploadApp instanceOf documentPlatform.uploadService`, and `workerApp instanceOf documentPlatform.processingWorker`. Put known platform facts on the zone or cluster description instead of fabricating VM details. Normal application traffic is still inherited through `instanceOf`; only add deployment edges for true infrastructure-only interactions. If the discussion shifts into DMZ/AppTier/ProcTier zoning or firewall boundaries, route that part to `structure-deployment-tiers`.
