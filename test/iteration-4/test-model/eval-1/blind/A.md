In a C2 detail view, validate the parent context by checking the included set, not just the parser result: the user should be one of the actor kinds from `projects/shared/spec-context.c4`, the web application and API should be container kinds from `projects/shared/spec-containers.c4`, and nothing from `projects/shared/spec-components.c4` should sneak in. Then inspect each include rule and ask what else it can match: exact FQNs are safest, while broad filters such as all `#Container` elements are risky because every container kind carries that tag. A quick sanity test is that every included container should share the same system prefix in its FQN, while the user sits outside that system boundary. If the rule could also pull sibling containers, other APIs, or any component-level element, the parent context is too broad.
