## 3. The executable validity paradox

The skill gets a slightly **lower** executable validity score than without_skill (0.50 vs 0.60), despite winning all blind comparisons.

**Interpretation:** The automatic checker (`analyze_likec4_snippet`) extracts LikeC4 snippets from responses and checks brace balance + known kinds. with_skill responses include more **shell commands** (`npx likec4 validate ...`) and fewer extractable DSL blocks, which mechanically reduces the number of applicable evals. At the same time, DSL snippets generated by with_skill may use more complex syntax (e.g. `variant sequence`) that the checker does not cover.

**Conclusion:** Executable validity is a weak proxy for DSL quality; it measures basic structural syntax (braces, kinds declared in spec-showcase), not semantic correctness or feature availability. This metric should not weigh heavily in skill revision decisions.

## 4. Assessment of skill design

### Strengths

1. **Accurate CLI coverage.** The skill provides exact flags for commands such as `validate`, `export png`, etc. This is exactly the type of information the baseline cannot infer, and it drives the gains in evals 0 and 2.
2. **Critical DSL keywords.** `variant sequence` is not documented in general literature; the skill makes it accessible (eval 3).
3. **Conciseness.** +30% expectations passed with 25% fewer words — the skill removes noise without sacrificing quality.
4. **No high-variance evals.** Results are stable, suggesting a reproducible skill advantage (even though there is only one run).

### Weak areas

1. **`$schema` in configuration (eval 1).** The baseline omits this required field. The skill fixes this, but the delta remains marginal (4/5 → 5/5). An explicit “required field” note in config examples would strengthen the signal.
2. **Selectors `*` vs `**` (eval 4).** The distinction is subtle and the baseline gets it wrong. The skill corrects this implicitly, but a dedicated paragraph in predicate reference would improve robustness.
3. **Deployment context (eval 5).** The win has low confidence (medium) and rests on contextual completeness detail, not on a missing feature. This eval is weakly discriminative.
4. **Single run.** With only one run per config, variance is zero by construction. A second run would check result stability, especially for evals 4 and 5 where margins are narrow.

## 6. Priority recommendations

**P1 — Critical (direct impact on baseline failures)**
1. Add a “Common commands and frequent mistakes” section in the CLI reference — explicitly state that `validate` is the correct command (not `check`, `lint`, `verify`), with the full example: `npx likec4 validate --json --no-layout --file .`
2. Highlight `variant sequence` in the sequence views section with an annotated example — this is the most frequently omitted feature by the baseline.

**P2 — Important (improved precision)**
3. Add `"$schema": "..."` to all `likec4.config.json` examples, marked as “(required)”.
4. Add a note on `*` vs `**` in predicate reference: “`*` selects direct children only; `**` selects all recursive descendants.”

**P3 — Nice to have (robustness)**
5. Run a second benchmark pass to validate stability on evals 4 and 5 (narrow-margin wins).
6. Consider an eval 6 specifically targeting arrow direction in sequence views (`->` for call, `<-` for return) — the baseline consistently fails on this point.
