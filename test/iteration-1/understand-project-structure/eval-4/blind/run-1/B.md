If you come from UML or ArchiMate, learn the repo's local conventions before drawing anything: project boundary first, then exact LikeC4 taxonomy, then id naming. In this workspace, real examples show that kinds are explicit repo-defined tokens such as `Container_Api`, `Container_Queue`, and `Component`; relationships are short controlled verbs such as `calls`, `reads`, `writes`, and `async`; tags echo category or layer markers like `Container`, `Api`, `Queue`, `Component`, and `Geo`; and C3 structure is modeled as children under a container, for example `api_container.*`. The real sources of truth are the target project's `likec4.config.json`, the shared specs under `projects/shared/spec-*.c4`, and the model files such as `projects/template/system-model.c4`, `projects/spec-showcase/containers.c4`, and `projects/spec-showcase/components.c4`; view files are downstream projections. After that orientation, hand off to `c4-modeling-process` to sequence the actual modeling work safely.
