Validation plan: 1) Resolve the new worker by exact FQN and confirm it sits under the same parent system as the existing containers; in the template project the C2 siblings are `mySystem.webapp`, `mySystem.api`, and `mySystem.database`, so a new worker should normally look like `mySystem.<workerName>`, not a new top-level element. 2) Confirm the worker uses a container kind that matches the project taxonomy, not an actor, system, or component kind. 3) Inspect the worker’s direct incoming and outgoing relationships and verify every endpoint uses the intended FQN, with the right direction, label, and technology. 4) Inspect each peer element that should connect to it and make sure the reciprocal incoming/outgoing edge is visible there too; this catches typos and one-sided assumptions. 5) Check view membership: the worker itself should be present in the dedicated C2 view and, only if intended, in the broader container view. 6) Check relationship membership as well: the new worker edge must appear in the dedicated C2 view, otherwise the model may be valid while the rendering is incomplete. 7) Validate rendering: the worker should render with container-style shape/color and should not appear orphaned, duplicated, or cross-scoped. 8) Finish with a manual C2 sanity check: parent system context is still obvious, labels are readable, and only the expected nodes and edges are shown.
