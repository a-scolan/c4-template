Use the shared deployment kinds from the repository spec: `Node_Environment` -> `Zone` -> `Node_Vm` -> `Node_App`. For your production setup, a clean structure is: `Prod = Node_Environment`, then zones such as `Dmz`, `AppTier`, `ProcTier`, and `DataTier`, then VMs like `ProdApigwVm`, `ProdUploadVm`, `ProdWorkerVm`, and `ProdMongoVm`, and inside each VM a `Node_App` such as `apiApp`, `uploadApp`, `workerApp`, and `mongoApp`. VM names should follow `{Environment}{Service}Vm`, so `ProdUploadVm` is correct.

Each `Node_App` should link to the logical model with `instanceOf <container FQN>`, for example the API app points to the API gateway container, the upload app points to the upload service container, and so on. Use the container FQNs from the system model, not ad-hoc names.

Do not copy normal application deployment relationships manually. The default rule in this skill is that relationships are inherited automatically through `instanceOf`. Put the business traffic and its technology on the logical model relationships, then let the deployment instances inherit them. Only add deployment relationships when they are truly infrastructure-specific, such as monitoring, backups, bastion access, or replication.

Also keep the VM and zone descriptions rich and operational: zones should document VLAN/CIDR and firewall intent, and VMs should document `eth0` first, then OS, CPU, RAM, disk, port, monitoring, and RTO.
